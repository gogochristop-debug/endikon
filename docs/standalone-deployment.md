# ENDIKON Standalone — per-law-firm deployment architecture

## Commercial decision

ENDIKON is distributed as **one isolated deployment per law firm**, with a one-time license/installation fee. It is **not** a shared multi-tenant SaaS. Ongoing hosting, maintenance, upgrades and support are separately contracted. One-time pricing must not be represented as lifetime free hosting or support.

## Isolation contract (required for every customer)

| Component | Per-customer resource |
| --- | --- |
| Cloudflare Worker | Unique service name, e.g. `endikon-<customer-slug>` |
| Cloudflare D1 | Dedicated database, never shared with another law firm |
| Cloudflare R2 | Dedicated private bucket |
| Domain | Customer-controlled domain and HTTPS |
| Cloudflare Access | Customer-specific application, audience and allowed administrators |
| Secrets | Customer-specific, provisioned outside Git |
| Backups and retention | Separate backup policy, restore drill and documented retention |
| Logs and support access | Scoped to the customer, least privilege, documented support access |

A distinct database and bucket are **not sufficient** if the same Access policy, admin email, secrets, service binding, backup or log sink can cross customer boundaries. Review every binding and external integration.

## Provisioning process

1. Obtain written agreement, scope, license, customer contact and data processing terms.
2. Choose a customer slug (non-sensitive identifier) and a unique Cloudflare account or explicit delegated ownership model.
3. Provision a new D1 database and private R2 bucket. Record their identifiers in a customer-specific **untracked** Wrangler configuration, not in the shared repository.
4. Configure unique Worker name, custom domain, Access application, Access audience and administrator allowlist. Do not reuse `ACCESS_ADMIN_AUD` or `ACCESS_ADMIN_EMAIL` from another customer.
5. Provision production secrets through Cloudflare's secure secret management. Never commit secrets or client data.
6. Apply all migrations to the dedicated D1 **after a backup**, including `0006_crm_foundation.sql`. Confirm schema and constraints. Do not assume a CI SQLite test applied remote migrations.
7. Build and deploy from a pinned release tag; run admin readiness checks and authenticated end-to-end acceptance tests.
8. Test role isolation, IDOR/cross-case access, private R2 object access, upload validation, backup restore and rollback.
9. Complete privacy/security and professional-confidentiality review. Obtain signed customer acceptance before enabling real data.
10. Deliver admin handover, domain/Cloudflare ownership documentation, support process, license and release version.

## Configuration rules

The repository's current `wrangler.jsonc` references shared **development** resources named `endikon-dev` and `endikon-documents-dev`. Never deploy these values for a customer. Do not edit this file to switch customers in the main branch; instead use a customer-specific generated configuration outside version control, or a controlled release pipeline that substitutes only explicitly validated non-secret resource identifiers.

A future provisioning script must validate uniqueness of Worker name, D1 database ID, R2 bucket, Access audience, domain and environment; fail closed if any value equals the development defaults or is missing.

## White-label settings (planned, not implemented by this document)

Provide per-installation settings for legal name, logo, address, contact details, preferred locale, theme, enabled service pages, privacy notice and terms. Validate branding assets and sanitize public content. Keep product code common; customer branding must not require editing shared application logic.

## Licensing model (proposed)

- One-time fee: license to use one installation, deployment, setup, training and an agreed acceptance window.
- Optional recurring service: hosting administration, backups, monitoring, security updates and support, priced and billed separately.
- Contract specifies who owns the Cloudflare account/domain, data export on termination, source-code rights, updates, support response times and responsibility for regulatory notices.

## Current blockers

This is an architecture decision and deployment checklist, **not a completed standalone installer**. Production identity, real client/case permissions, private uploads, client portal, verified migrations, full legal/privacy review, backup/restore and end-to-end security tests remain mandatory before selling as a production legal case-management system.
